# Adaptive Optopatch: acquisition and analysis design

## Integration boundary

Adaptive Optopatch runs in the MATLAB process that owns the live Luminos app.
The React interface remains responsible for rig startup, alignment, calibration,
manual inspection, and emergency intervention. Adaptive Optopatch reads and
configures the existing MATLAB device objects and requests acquisitions through
Luminos; it does not independently open NI or camera hardware.

Live execution remains disabled until the remaining calibration and feedback
checks below are confirmed. The 2026-07-28 VU acquisition now establishes the
first-pass ports, synchronized task routing, and saved-data representation.

## Active Luminos settings

At the start of a run, the runner captures a complete, immutable snapshot of
the active Luminos settings. The GUI presents editable working copies of
settings relevant to the experiment. Each field is marked as:

- `inherited`: taken unchanged from the active Luminos session;
- `overridden`: explicitly changed by the experimenter;
- `record_only`: shown and archived but not changed by Adaptive Optopatch.

The snapshot, requested overrides, and settings read back immediately before
each acquisition are saved with the run manifest. Camera ROI, exposure, frame
rate, imaging illumination, scanner state, calibration identifiers/transforms,
DAQ clock/trigger configuration, and waveform definitions are included where
the Luminos objects expose them.

From `src/Applications/Virtual_Upright/Virtual_Upright.json`:

| Property | Value |
|---|---|
| Device type | `NI_DAQ_Modulator` |
| Device name | `2P mod` |
| Port | `Dev1/ao3` |
| Minimum command | `0 V` |
| Maximum command | `5 V` |
| Scanner | `Chameleon (To friends: Ben)` |
| Scanner voltage bounds | `[-5, -5, 5, 5] V` |
| Scanner sample rate | `200000 Hz` |

The rig file does not specify optical power or a voltage-to-power calibration.
The experimenter will select the minimum effective power manually in Luminos.
`0 V` is the minimum Pockels-cell command but does not mechanically block all
light; positive voltage increases light. Adaptive Optopatch records the active
setting and uses it as the requested pulse amplitude after explicit
confirmation. Until that confirmation, the default command is `0 V`.

## VU 1P blue-DMD device facts

The automated 1P runner uses the following declarations from
`Virtual_Upright.json`:

| Role | Luminos device | Hardware endpoint |
|---|---|---|
| Spatial targeting | `DMD_Blue` (`ALP_DMD`) | Luminos DMD API |
| Light source | `488` (`OBIS_Laser`) | `COM9`, maximum `0.055 W` |
| Millisecond gating | `mod488` | `Dev1/ao2`, `0-5 V` |
| Acquisition shutter | `shutter488` | `Dev1/port0/line0` |
| Voltage timing clock | Camera 1 HSYNC | `Dev1/PFI0`, `200 kHz` |

The OBIS serial power is a ceiling/setpoint; individual 5-10 ms pulses are
generated by the camera-clocked `mod488` AO waveform. The shutter is opened
before each acquisition and closed immediately afterward, rather than being
cycled for each pulse. Live preflight requires OBIS `ANALOG` or `MIXED` mode,
an enabled key/interlock, a nonidentity `DMD_Blue` transform with calibration
reference, and the Camera 1 HSYNC waveform clock. The runner preserves the
active Luminos timing configuration and replaces only the `mod488` output.

## Connectivity-screen protocol

One Luminos acquisition is made per stimulated neuron. All 200 test pulses are
contained in that acquisition.

| Parameter | Initial value |
|---|---|
| Pulse count | 200 |
| Pulse duration | editable, default `5 ms`, allowed design range `5–10 ms` |
| 2P modulator command | `0 V` pending calibration |
| Prestimulus delay | `100 ms` |
| End-to-start dark interval | independent uniform jitter from `45–55 ms` |
| Poststimulus delay | `100 ms` after the final pulse ends |
| Acquisitions per neuron | 1 |

The random seed and the complete realized pulse-time vector are saved before
acquisition. Acquisition duration is calculated from that realized vector:

`duration = pre_delay + sum(all pulse durations) + sum(end-to-start intervals) + post_delay`

At the default mean interval and 5 ms pulse duration, the expected duration is
approximately `11.15 s`. With 200 pulses and 199 independently jittered gaps,
the possible range is approximately `10.155–12.145 s`. At a 10 ms pulse
duration, the expected duration is approximately `12.15 s`.

The scheduler constructs each new onset as:

`next_onset = previous_onset + previous_pulse_duration + sampled_dark_interval`

This guarantees that pulses cannot overlap, including when pulse duration is
changed.

## Rapid preprocessing and trace extraction

The first-pass fast analysis uses:

1. Optional rigid translation correction, with shifts and registration quality
   recorded. NoRMCorre/DFT rigid registration is already present in Cohen-lab
   analysis code.
2. Mean fluorescence for each soma ROI.
3. Background correction selected per run:
   - a local annulus around each soma, excluding all soma masks; or
   - one experimenter-drawn null/background ROI shared across cells.
4. No photobleaching correction by default for these short recordings.
   Cohen-lab code supports several bleaching corrections, including biexponential
   baseline correction, but lab scripts also commonly disable it for short
   voltage-imaging analyses. It remains an optional QC-controlled setting.
5. Stimulus-triggered response amplitude, latency, noise, and trial consistency.

The analysis ranks directed candidate pairs for manual review; it does not
automatically commit pair selection.

## STF protocol model

An STF acquisition targets one presynaptic neuron and contains a randomized,
intermixed event list. Conditions can include:

- single-pulse controls;
- pulse trains at user-selected frequencies up to `100 Hz`;
- configurable pulse counts, pulse durations, and modulator commands;
- no-light/null events;
- configurable repeats per condition and recovery intervals.

For example, one acquisition can contain 100 single-pulse events, 100 50-Hz
trains, and 100 100-Hz trains in one randomized sequence. The realized event
order, pulse times, and condition identity are generated and saved before the
acquisition starts. Acquisition duration is calculated from the complete
realized schedule.

## Runner state machine

Each manifest row moves through:

`planned -> preflight_passed -> configured -> acquiring -> completed -> analyzed`

Failures move to `failed` with the exception, device snapshot, and last known
output directory recorded. The runner supports stop-after-current-acquisition
and resume-from-first-incomplete-row. Hardware errors are not automatically
retried.

Preflight checks include:

- correct rig and voltage camera;
- current scanner/DMD calibration present and nonidentity where required;
- expected devices, ports, clocks, and triggers;
- requested commands within rig-file electrical bounds;
- sufficient output storage;
- acquisition duration compatible with active camera settings.

Immediate abort remains a Luminos/operator function. Adaptive Optopatch also
provides a stop-after-current-acquisition control.

## Safety-limit categories

Adaptive Optopatch treats rig protection and specimen protection as separate
preflight layers.

### Hard hardware and electrical constraints

These are properties of the rig or device and should normally come from the
rig initializer or device API:

- `2P mod` analog output range: `0–5 V`;
- scanner command bounds: `-5–5 V` on each axis;
- scanner sample rate and waveform-buffer constraints;
- valid DAQ ports, clocks, trigger routes, and supported voltage ranges;
- laser, modulator, shutter, galvo, and DAQ manufacturer limits, if exposed by
  their device definitions or manuals.

Requests outside a hard hardware constraint are always rejected. These limits
protect electronics, modulators, scanners, and lasers, but they do not establish
that a protocol is safe for a biological sample.

Biological exposure limits are not enforced by the first live runner. Power
selection and biological suitability remain the experimenter's responsibility.
The run record still stores voltage, pulse timing, scan geometry, and cumulative
on-time so exposure can be audited later.

### Required hardware-control confirmations

Before live output, confirm:

1. Which Luminos/DAQ sample clock and rate should generate the modulator
   waveform. This will normally be inherited from the saved live protocol.
2. That `Dev1/ao3` is not simultaneously owned by another active DAQ task or
   waveform.
3. The scanner transform is current, its requested path remains within
   `[-5,5] V`, and fixed-repetition-rate mode is either intentionally configured
   or disabled.
4. The active pulse amplitude shown in React maps to the raw AO voltage expected
   by the waveform API, particularly if the modulator object's `iscalibrated`
   flag is enabled.

Adaptive Optopatch validates every generated AO sample against `0–5 V`, requires
the waveform length to match the finite DAQ task length, verifies clock and
trigger routes, and commands `2P mod = 0 V` on normal completion, error, stop,
and abort cleanup.

### Galvo protection

Point density alone is not a sufficient galvo-safety metric. At a fixed
`200 kHz` update rate, increasing `Points_Per_Volt` generally reduces the
distance between consecutive samples and lowers the spiral repetition rate.
Galvo preflight therefore evaluates the final calibrated voltage waveform:

- X/Y command extrema against scanner bounds;
- maximum first difference in V/sample and V/s;
- maximum second difference in V/sample² and V/s²;
- the wrap discontinuity from the last sample back to the first;
- waveform repetition rate;
- continuous scan duration;
- measured X/Y feedback error, when feedback acquisition is active.

Luminos's `Calculate_Spiral_Scan` begins at the center and ends near the outer
radius. The source-visible MATLAB path does not explicitly append a return
trajectory before passing the waveform to `Update_Galvos_Explicit`. Adaptive
Optopatch requests an outward Fermat spiral followed by a mirrored inward
spiral. Radius decreases on the return while polar angle continues increasing.
The two paths are spatially interleaved rather than retraced. The outer endpoint
is not duplicated. This removes the outer-radius-to-center wrap step, avoids
reversing angular velocity, returns to the center, and nearly doubles the
samples per complete scan.

Radial velocity must still change sign at the outer turnaround. Preflight
therefore evaluates that acceleration. If feedback tests show tracking error,
the generator will add a short rounded radial transition.

Numerical rejection thresholds for velocity, acceleration, tracking error, and
continuous operation cannot be derived from `Virtual_Upright.json`. They require
the galvo scanner and servo-controller model/rating, or conservative limits
measured from a known long-running Luminos scan protocol. Live automated spiral
repetition remains disabled until one of these sources is available.

For the Thorlabs GVS002, the conservative initial model uses:

- analog position input range: `+/-10 V`;
- maximum mechanical angle: `+/-12.5 degrees` at `0.8 V/degree`;
- selectable input scaling: `0.5`, `0.8`, or `1.0 V/degree`;
- small-angle (`+/-0.2 degree`) bandwidth: `1 kHz`;
- small-angle settling time: `300 microseconds`;
- full-scale repetitive limits of `100 Hz` for square-like motion, `175 Hz`
  for triangle/sawtooth-like motion, and `250 Hz` for sinusoidal motion;
- average and peak motor-current ratings of `1 A` and `5 A`;
- operating temperature range: `0–40 C`.

The runner cannot infer coil current from command voltage, so it uses command
bandwidth and measured position feedback as observable protections. Until the
driver-board input-scale switch is confirmed, angle checks use the most
conservative conversion. Large-angle repetitive scans are capped at `100 Hz`;
the `1 kHz` rating is used only when each axis remains within `+/-0.2 degree`.
For an outward-plus-continuous-return waveform, repetition rate is:

`scanner_sample_rate / (2 * native_spiral_samples - 1)`

During each requested optical pulse, the double spiral repeats continuously.
At the requested pulse end, the Pockels command returns to `0 V`; the currently
active spiral then completes its inward return to the target center. With the
Pockels command remaining at `0 V`, the galvos follow a smooth transition to a
cell-free parking point and remain there during the dark interval. Before the
next optical pulse, they return to the target center and settle while the
Pockels command remains at `0 V`.

The initial parking strategy is local and target-specific. Adaptive Optopatch
searches outside the stimulation footprint plus a clearance margin but within
two spiral diameters of the target by default. It excludes every soma mask and
image edges, then selects the darkest valid local region in a spatially averaged
reference image. Averaging over a small disk avoids selecting an isolated dead
or noisy camera pixel. The parking coordinate, travel distance, clearance,
local mean intensity, search radius, selection method, and QC result are saved
per target and displayed in magenta in the preview.

When a nonidentity scanner transform is archived, the preview converts spiral
radius into scanner volts and calculates the exact double-spiral sample count:

`outbound_samples = round(pi * radius_volts^2 * Points_Per_Volt^2)`

`cycle_samples = 2 * outbound_samples - 1`

The preview reports fractional cycles during the optical pulse, complete cycles
while light is on, cycles started before light turns off, and cycle duration.
Without a calibrated transform these values are reported as pending.

## Remaining external inputs

Required before live 2P execution:

1. A valid camera-to-galvo calibration. The transform archived in
   `1454092P_test` maps a soma-sized camera displacement outside the ±5 V
   command domain and is rejected by preflight.
2. Confirmation of how the active React power setting maps to the AO waveform
   amplitude.
3. GVS002 driver-board input scale (`0.5`, `0.8`, or `1.0 V/degree`).
4. A short commanded-versus-feedback galvo recording.

The reference acquisition confirms `2P mod = Dev1/ao3`, galvo X/Y on
`Dev2/ao0-1`, feedback inputs on `Dev2/ai1-2`, a 200 kHz sample rate,
`Internal Dev1` master timing, `Dev1/PFI12 -> Dev2/PFI0` clock bridging, and
device-local triggers on `Dev1/PFI9` and `Dev2/PFI1`. It did not include an AI
feedback task, so its sine test is evidence of command generation only.
